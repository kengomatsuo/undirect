# What Google and Bing document that a small static marketing site must do (research for ASG50, 2026-11-20)

Sites this drives: matsuokengo.com (plain HTML, Cloudflare Pages), undirect.matsuokengo.com (~153 URLs, ~30 languages, GitHub Pages) and cutling.matsuokengo.com (~421 URLs, ~75 languages, GitHub Pages). Search Console on 2026-11-20: 14 of 587 URLs indexed, 561 "Discovered - currently not indexed" with last crawl N/A, no Undirect page indexed, no structured data detected, IndexNow 403 for Undirect.

Every row below was fetched this run (curl of the vendor page, text read in full, 2026-11-20) unless marked UNREAD. "Means here" is what the doc implies for these three sites; it is analysis, not the vendor's words. AI-crawler and llms.txt research is in `ai-files-research.md` and not repeated. Live-site and Search Console readings are in `seo-research.md`.

## 1. Crawl budget and "Discovered - currently not indexed"

| What the doc says | URL read | Means here |
|---|---|---|
| Google treats each hostname as a separate site with its own crawl budget: `www.example.com` and `code.example.com` are separate. Every site starts with "the same default, conservative crawl capacity limit", raised over time only "if there is demand to crawl more and the site remains healthy". | https://developers.google.com/crawling/docs/crawl-budget (redirected from /search/docs/crawling-indexing/large-site-managing-crawl-budget) | undirect.matsuokengo.com and cutling.matsuokengo.com each start from zero history, separate from matsuokengo.com. Nothing from the parent domain's standing carries over in crawl allocation. |
| Crawl demand for Googlebot "varies based on a site's size, update frequency, page quality, and relevance, compared to other sites". The factors you influence: perceived inventory (duplicates waste time, "the factor that you can positively control the most"), popularity ("URLs that are more popular on the Internet tend to be crawled more often"), staleness. "Even if the crawl capacity limit isn't reached, if crawl demand is low, Google will crawl your site less." | same | 561 URLs never fetched is low *demand*, not server capacity: brand-new hosts with no inbound links and hundreds of near-identical translated pages. The levers are fewer duplicate-looking URLs and links from the outside web, not faster servers. |
| The guide names "Sites with a large portion of their total URLs classified by Search Console as Discovered - currently not indexed" as one of its three audiences, alongside 1M+ page sites. | same | Google itself treats this report status as a crawl-budget symptom, so the guide applies to these small sites despite their size. |
| Best practices: consolidate duplicate content ("focus crawling on unique content rather than unique URLs"); don't use `noindex` to save budget (Google still fetches); return 404/410 for removed pages; "Eliminate soft 404 errors. soft 404 pages will continue to be crawled, and waste your budget"; keep sitemaps up to date with `<lastmod>`; avoid long redirect chains; make pages load fast; support 304 Not Modified. | same | matsuokengo.com's catch-all 200 (every path returns the home page) is a soft-404 generator that wastes budget. The 12 "Page with redirect" URLs (no trailing slash) are links pointing at redirects; fix the links. |
| "How do I get more crawl budget?": add server resources, or "Optimize your content's quality ... for Google Search, this includes things like popularity, overall user value, content uniqueness, and serving capacity." | same | Content uniqueness is named outright: 30-75 translations of the same short marketing page are low uniqueness per URL. |
| "Discovered - currently not indexed: The page was found by Google, but not crawled yet. Typically, Google wanted to crawl the URL but this was expected to overload the site; therefore Google rescheduled the crawl. This is why the last crawl date is empty on the report." | https://support.google.com/webmasters/answer/7440203 (Page indexing report help) | The official wording blames expected load. For GitHub Pages hosts that is a conservative starting limit on a new hostname (see crawl budget row 1), not real overload; demand signals are what raise it. |
| "Crawled - currently not indexed ... Google doesn't index all pages across the web, so this is a common message". "Don't expect every URL on your site to be indexed. Some URLs might be duplicates or might not contain meaningful information. Just be sure that the key pages on your site are indexed." Common cause of more non-indexed than indexed pages: "a large number of duplicate pages". | same | The goal Google sets is "key pages indexed", not 587 of 587. Get each site's English home, feature pages and comparison pages in first (URL Inspection > Request indexing), then let languages follow. |
| "Alternate language pages are not detected by Search Console" as "Alternate page with proper canonical tag"; "Page with redirect: This is a non-canonical URL that redirects to another page ... will not be indexed." | same | The 12 redirect URLs are harmless as long as their targets are the URLs linked and listed; translated pages will not show as "alternate", they must each be indexed on their own merit. |

## 2. Localized versions and hreflang

| What the doc says | URL read | Means here |
|---|---|---|
| "Localized versions of a page are only considered duplicates if the main content of the page remains untranslated." | https://developers.google.com/search/docs/specialty/international/localized-versions | Fully translated pages are not duplicates of English by Google's definition. Pages where only the nav is translated and the body stays English would be. |
| HTML `<link>`, HTTP `Link:` header and sitemap `xhtml:link` "are equivalent from Google's perspective ... there's no benefit in Search" to using more than one. "Google doesn't use hreflang or the HTML lang attribute to detect the language of a page; instead, we use algorithms". | same | Pick one method per site. Both app sites currently ship hreflang in the sitemap (754 KB and 2.6 MB); if the pages' `<head>` also carry it, one copy is redundant weight. The visible text decides the language, not `lang=`. |
| Rules for every method: "Each language version must list itself as well as all other language versions"; URLs fully qualified with scheme; may be cross-domain; "If two pages don't both point to each other, the tags will be ignored." Large sets may omit some languages, but link new languages bidirectionally to the dominant one. | same | Self-reference and reciprocity are mandatory; a generator that builds the set once and prints it identically on every member satisfies both. |
| `x-default`: "Consider adding a fallback page for unmatched languages, especially on language/country selectors or auto-redirecting home pages ... it was designed for language selector pages and so it will work best with those." | same | The root `/` with a locale router is exactly the case x-default is for: point x-default at the root (or at English). |
| In the sitemap: each `<url>` lists every variant including itself; "Child elements don't count towards the URL limit for sitemaps"; a sitemap can only contain descendant URLs of its directory. | same | 421 URLs x 75 alternates is fine against the 50,000-URL limit; only the 50 MB size limit applies (2.6 MB now). |
| Codes: ISO 639-1 language, optional ISO 3166-1 alpha-2 region, or ISO 15924 script (`zh-Hans`, `zh-Hant`). "other codes that aren't listed in those standards, such as es-419, aren't supported." Region alone is invalid; `UK`, `EU`, `UN` are ignored. | same | Any `es-419` (Latin American Spanish, common in App Store locale lists) in the generators is silently ignored by Google; use `es-MX` or plain `es`. Check every code the two generators emit. |
| Common mistakes: missing return links, incorrect language codes, incorrect region codes. Google points to third-party testers (Aleyda Solis generator, Merkle tester). | same | A build-time check that every hreflang set is symmetric and every code is ISO-valid catches all three. |
| "Google recommends using different URLs for each language version"; if you "reroute the user based on language settings, be aware that Google might not find and crawl all your variations ... the crawler sends HTTP requests without setting Accept-Language". "Avoid automatically redirecting users from one language version of a site to a different language version ... These redirections could prevent users (and search engines) from viewing all the versions." Add links to other language versions instead. | https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites | A JS locale router on the root is tolerated only on a root that is itself a selector/x-default page with plain `<a href>` links to every language; it must never move a visitor off a language page they asked for. Googlebot (no Accept-Language) would always see the router's fallback. |
| "Google uses the visible content of your page to determine its language. We don't use any code-level language information such as lang attributes, or the URL." Use one language per page; avoid side-by-side translations. Translating only boilerplate "can create a bad user experience". | same | Pages that mix English feature text with translated chrome get detected as English and compete with the English page. |
| Locale-adaptive pages (content varying by IP or Accept-Language) may not be crawled for every locale; "We recommend using separate locale URL configurations and annotating them with rel="alternate" hreflang annotations." Googlebot IPs "appear to be based in the USA". | https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages | Confirms: separate URLs per language (which both app sites have) plus hreflang; the root router must not be the only way to reach a language. |
| Scaled content abuse: "many pages are generated for the primary purpose of manipulating search rankings and not helping users ... no matter how it's created." Examples include generative-AI pages "without adding value" and "Scraping feeds ... (including through automated transformations like synonymizing, translating, or other obfuscation techniques), where little value is provided to users". | https://developers.google.com/search/docs/essentials/spam-policies | Translation is named only as a transformation of scraped content. Translating your own product page for real speakers of that language is not the listed abuse; the test is whether a reader of that language gets value. Machine-translated pages nobody reviewed are the risk. |
| Doorway abuse includes "Creating substantially similar pages that are closer to search results than a clearly defined, browseable hierarchy" and pages "targeted at specific regions or cities that funnel users to one page". Keyword stuffing includes blocks of text listing places or repeated phrases. | same | Comparison and "alternative to X" pages must each carry distinct facts; a template that swaps only the competitor's name reads as doorway pages. |
| Sneaky redirects: redirecting "to either show users and search engines different content or show users unexpected content". Legitimate redirects include consolidating pages. | same | A language router that sends the same visitor (or Googlebot) somewhere different from what they asked for is the pattern to avoid; a redirect from `/en-us` to `/en-us/` is legitimate. |

## 3. Sitemaps

| What the doc says | URL read | Means here |
|---|---|---|
| "All formats limit a single sitemap to 50MB (uncompressed) or 50,000 URLs"; beyond that split and optionally use a sitemap index. File must be UTF-8. A sitemap at the root covers the whole site; use absolute URLs; list only the canonical URLs you want in results. | https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap | Both app sitemaps are well inside the limits (754 KB / 153 URLs, 2.6 MB / 421 URLs). Every `<loc>` must be the exact canonical form (with trailing slash), or Google crawls a redirect. |
| "Google ignores `<priority>` and `<changefreq>` values." "Google uses the `<lastmod>` value if it's consistently and verifiably ... accurate." It should reflect "the last significant update" (main content, structured data or links), "however an update to the copyright date is not". | same | A generator that stamps every URL with the build date on each deploy makes lastmod unverifiable and Google stops trusting it. Stamp lastmod from the page's content hash changing (or the git date of its source strings). Drop priority/changefreq. |
| "submitting a sitemap is merely a hint". Ways to submit: Search Console Sitemaps report, Search Console API, or a `Sitemap: https://example.com/my_sitemap.xml` line "anywhere in your robots.txt"; multiple lines allowed, no limit. | same | matsuokengo.com needs a real sitemap.xml and a `Sitemap:` line in robots.txt (today it has neither, and `/sitemap.xml` is a soft 404). The app sites' robots.txt must name their sitemaps too, so Bing and others find them without Search Console. |
| Cross-site submission: one sitemap may list URLs on other verified hosts if submitted through Search Console, or each site's robots.txt can point at a sitemap hosted elsewhere. | same | Possible but unnecessary: each host can serve its own. |
| Sitemap index: same rules as sitemaps; referenced sitemaps must be on the same site and in the same or a deeper directory; up to 50,000 `<loc>` per index; up to 500 index files per site in Search Console; optional `<lastmod>` per child sitemap in W3C Datetime. | https://developers.google.com/search/docs/crawling-indexing/sitemaps/large-sitemaps | Not needed at this size. A per-language or per-page-type split would only help by giving per-sitemap indexing counts in Search Console, which is a real diagnostic benefit for finding which languages Google refuses. |
| "You might not need a sitemap if: Your site is 'small' ... about 500 pages or fewer"; "You might need a sitemap if ... Your site is new and has few external links to it. Googlebot ... might not discover your pages if no other sites link to them." "it doesn't guarantee that all the items in your sitemap will be crawled and indexed." | https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview | The sites are new with few external links: that is the case Google names. The sitemap gets URLs discovered (it did: 561 discovered); only demand gets them crawled. |

## 4. Structured data (Google)

| What the doc says | URL read | Means here |
|---|---|---|
| SoftwareApplication rich result **required**: `name`, `offers.price` (set `0` if free; add `priceCurrency` when > 0), and a rating or review: "You must include one of" `aggregateRating` or `review`, following the Review snippet guidelines. **Recommended**: `applicationCategory` (one of 22 values incl. `UtilitiesApplication`, `BrowserApplication`, `ProductivityApplication` is *not* in the list; `BusinessApplication`, `DesktopEnhancementApplication`, `SecurityApplication` are), `operatingSystem`. `MobileApplication` and `WebApplication` subtypes supported. Page last updated 2026-09-08. | https://developers.google.com/search/docs/appearance/structured-data/software-app | Without a rating or review on the page, the app pages are not eligible for the software-app rich result at all; the markup still helps Google and other consumers understand the entity. Undirect fits `BrowserApplication` or `SecurityApplication`; Cutling fits `UtilitiesApplication` (or `BusinessApplication`). |
| Review snippet guidelines: "Don't aggregate reviews or ratings from other websites." Review content "must be readily available to users from the marked-up page" and "If you use AggregateRating, users should be able to see that aggregate rating on the page." No fake or undisclosed incentivized reviews (guideline added 2026-07-24). Self-serving reviews are barred for LocalBusiness and Organization (an entity controlling reviews about itself); Software App is listed as a supported review target without that bar. | https://developers.google.com/search/docs/appearance/structured-data/review-snippet | Copying the App Store rating into `aggregateRating` breaks "don't aggregate reviews or ratings from other websites". The only compliant route to stars is reviews collected and shown on the site itself, or one genuine `review` (for example an editor's review quoted *and* hosted on the page, which is still another site's review). Realistically: ship SoftwareApplication without stars and accept no rich result. |
| General guidelines: JSON-LD recommended; don't block marked-up pages; "Don't mark up content that is not visible to readers of the page"; "Your structured data must be a true representation of the page content"; required properties missing → not eligible; "If you have duplicate pages for the same content, we recommend placing the same structured data on all page duplicates"; all image URLs in structured data "must be crawlable and indexable". A structured data manual action removes rich-result eligibility but "doesn't affect how the page ranks". | https://developers.google.com/search/docs/appearance/structured-data/sd-policies | Every fact in the JSON-LD (price, OS, features) must also be visible text on the same page. Put the same markup on every language version (translated `name`/`description` allowed). |
| Organization: "There are no required properties"; place it "on your home page, or a single page that describes your organization ... You don't need to include it on every page". `logo`: "at minimum" 112x112 px, crawlable and indexable URL, a format Google Images supports, must look right on white. `name` should be "the same name and alternateName that you're using for your site name". `sameAs`: profile pages on social or review sites, multiple allowed. `url` "helps Google uniquely identify your organization". Page last updated 2026-09-08. | https://developers.google.com/search/docs/appearance/structured-data/organization | matsuokengo.com home carries `Organization` (or the owner as `Person`) with `logo`, `url`, `sameAs` to App Store developer page, GitHub, social accounts; each app site's root points back via `publisher`/`author` with the same `@id`. |
| Site names: generated automatically "from a site's home page and references to it that appear on the web"; `WebSite` structured data "is most important". Required: `name`, `url` (canonical home). Optional `alternateName` list. **"The WebSite structured data must be on the home page of the site. By home page, we mean the domain or subdomain level root URI ... https://example.com/de/index.html isn't the home page."** "If there's no structured data on the subdomain's home page, then the domain-level site name may be used for the subdomain as a fallback." One name per domain or subdomain; none at subdirectory level. Avoid generic names; be consistent with `og:site_name`, `<title>` and headings on the home page. | https://developers.google.com/search/docs/appearance/site-names | The `WebSite` block (`name: "Undirect"` / `"Cutling"`) must sit on `https://undirect.matsuokengo.com/` and `https://cutling.matsuokengo.com/` themselves, the root that runs the locale router, not only on `/en-us/`. Otherwise Google may label every Undirect and Cutling result with matsuokengo.com's site name. The root must also be crawlable content, not an empty redirect shell. |
| ProfilePage: required `mainEntity` (Person or Organization) with `name`; recommended `dateCreated`, `dateModified`, `sameAs`, `image`, `alternateName`. Valid: "An 'About Me' page on a blog site"; invalid: "The main home page of a store". "The primary focus of the page must be a single person or organization that is affiliated with the overall website." | https://developers.google.com/search/docs/appearance/structured-data/profile-page | matsuokengo.com (a developer's personal site, about one person) qualifies for `ProfilePage` with `mainEntity: Person` + `sameAs`, and `hasPart` can list the two apps. |
| Breadcrumbs: "available on desktop" only. Needs a `BreadcrumbList` of at least two `ListItem`s with `position`, `name`, `item` (last item may omit `item`). "We recommend providing breadcrumbs that represent a typical user path to a page, instead of mirroring the URL structure." | https://developers.google.com/search/docs/appearance/structured-data/breadcrumb | Worth adding on app subpages (Home > Compare > Paste, Home > Support) for desktop results; replaces the raw URL path shown under the title. |
| VideoObject: influences description, thumbnail, upload date and duration in video results; required/recommended per doc (example uses `name`, `description`, `thumbnailUrl`, `uploadDate`, `duration`, `contentUrl`, `embedUrl`). `creator` property added 2026-09-24. Key moments via `Clip` or `SeekToAction`. | https://developers.google.com/search/docs/appearance/structured-data/video | Search Console shows one page with a video, not indexed. A preview film on the app page gets `VideoObject` with a crawlable thumbnail; the video should be the page's main content for video-mode eligibility. |
| FAQ rich result: changelog 2026-05-08 "This feature will no longer appear in Google Search starting May 7, 2026"; June 2026 "Removed documentation for the FAQ rich result feature ... no longer shown in Google Search results". The old FAQPage doc URL now redirects to the changelog. The structured-data gallery no longer lists FAQ. | https://developers.google.com/search/updates (the old https://developers.google.com/search/docs/appearance/structured-data/faqpage redirects here); https://developers.google.com/search/docs/appearance/structured-data/search-gallery | FAQPage markup earns nothing in Google Search any more. Keep FAQ content as visible text (it helps answers and AI features); the JSON-LD is optional and only for other consumers (Bing, see section 9). |
| Other deprecations in the same changelog: practice problem (Jan 2026), course info, estimated salary, learning video, special announcement, vehicle listing (Sept 2025), sitelinks search box removed. | https://developers.google.com/search/updates | Do not add `SearchAction` for a sitelinks search box; it no longer does anything. |
| March 2026: "Google uses both schema.org markup and the og:image meta tag as sources when determining image thumbnails in Google Search and Discover." | https://developers.google.com/search/updates (entry "Added preferred image best practices") | `og:image` and the JSON-LD `image` should name the same crawlable picture. |

## 5. Google AI features (AI Overviews, AI Mode)

| What the doc says | URL read | Means here |
|---|---|---|
| "To be eligible to be shown as a supporting link in AI Overviews or AI Mode, a page must be indexed and eligible to be shown in Google Search with a snippet ... There are no additional technical requirements." "You don't need to create new machine readable files, AI text files, or markup to appear in these features. There's also no special schema.org structured data". Listed fundamentals: crawling allowed "by any CDN or hosting infrastructure", internal links, page experience, important content in text, images and video, structured data matching visible text. | https://developers.google.com/search/docs/appearance/ai-features | No Undirect page is indexed, so Undirect cannot appear in AI Overviews or AI Mode at all today. Indexing is the whole gate; nothing AI-specific substitutes for it. |
| AI optimization guide (added 2026-05-15, updated 2026-07-10): generative AI features "are rooted in our core Search ranking and quality systems" (RAG/grounding from the Search index, and "query fan-out"). "From Google Search's perspective, optimizing for generative AI search is ... still SEO." | https://developers.google.com/search/docs/fundamentals/ai-optimization-guide | ASG46 (be recommended by AI tools) and ASG50 (SEO) are the same work for Google: rank in classic search for the fan-out queries (e.g. "Safari redirect blocker", "clipboard manager iPhone keyboard"). |
| "Create valuable, non-commodity content": "a first-hand review provides a unique perspective ... Don't just recycle what others on the internet have already said, or could easily be produced by a generative AI model." Organize with headings; add high-quality images and video. | same | The app pages should carry what only the maker knows: how the guard decides, what Cutling stores and where, measured facts, the maker's own comparisons. Generic feature lists are commodity content. |
| "While it might be tempting to create separate content for every possible variation of how people might search (for example ... fan-out queries), doing so primarily to manipulate rankings or generative AI responses in Google Search violates Google's scaled content abuse spam policy." Also "a high quantity of pages doesn't make a website higher quality". | same | Do not generate a page per query or per competitor permutation. A handful of real comparison pages beats dozens of templated ones. |
| A page must be indexed and snippet-eligible, and "a site must be included in Search generative AI features in Search Console to be eligible". | same | Check the setting (below) once; default is included. |
| Search generative AI control (rolled out to all sites 2026-08-31): Settings > Search generative AI in Search Console; options Include (default for all properties), Exclude, Inherit from parent (default when a parent property exists). Excluding is not a ranking signal for other Search; it does not affect training (that is Google-Extended). | https://support.google.com/webmasters/answer/16908024 | The `sc-domain:matsuokengo.com` property is the parent of any subdomain property; confirm it reads Include. |
| Generative AI performance report (all sites since 2026-08-31): impressions from AI Overviews and AI Mode by page, country, device, date; "Not seeing the report? This usually happens when your site hasn't received enough impressions". | https://support.google.com/webmasters/answer/16984139 | The measurement for ASG46 on Google's side; expect it empty until pages are indexed. |
| Mythbusting: llms.txt and "other 'special' markup" are ignored by Google Search, "neither harm nor help"; no need to "chunk" content; no need to rewrite for AI or chase long-tail variants; "seeking inauthentic 'mentions' across the web isn't as helpful as it might seem"; "Structured data isn't required for generative AI search". Changelog 2026-06-15 repeats that llms.txt files "won't negatively or positively impact your visibility or rankings". | same; https://developers.google.com/search/updates | ASG44's llms.txt work serves other assistants, not Google. Planted mentions are named as not helpful; genuine third-party coverage is what the systems read. |
| AI agents section points to "agent-friendly website best practices" (web.dev/articles/ai-agent-site-ux) and the Universal Commerce Protocol. | same | Not read this run (UNREAD: https://web.dev/articles/ai-agent-site-ux); ASG44's research covered agent files. |
| Changelog 2026-05-15: "spam policies also apply to generative AI responses in Google Search". | https://developers.google.com/search/updates | Doorway or scaled comparison pages risk exclusion from AI answers as well as from results. |
| Search technical requirements: Googlebot not blocked; "Google receives an HTTP 200 (success) status code"; indexable content. "Client and server error pages aren't indexed." | https://developers.google.com/search/docs/essentials/technical | The baseline every page must meet; a soft 404 meets it technically and is still discarded (section 6). |
